## 2. 第一版草稿

# 《凝胶无法构筑大楼》

AI 像水。

它没有固定的形状，却可以流入几乎所有容器。写代码、改文档、分析日志、生成脚本，只要给出足够清晰的指令，它就能迅速填满任务留下的空隙。

但水也有明显的局限：它会流动，会蒸发，无法独立承重。

于是我们开始给 AI 加入 Skill。

Skill 为 AI 提供了相对稳定的流程、约束和领域知识。它告诉 AI 应该先检查什么、按照什么顺序操作、如何验证结果，以及遇到异常时怎样处理。原本四处流淌的水因此获得了一些结构，变成可以维持形态的凝胶。

可凝胶终究不是钢筋混凝土。

只依靠 AI 和 Skill，我们或许能快速塑造出一座大楼的轮廓，却无法保证它真正承重，更无法保证它经得住长期运行、复杂协作和持续变化。

## Skill 确实改变了我的开发方式

在实际开发过程中，我已经把 Skill 用在了不少地方。

发版曾经是一项繁琐而容易出错的工作。修改版本号、更新变更记录、创建 Git 标签、触发 GitHub Actions，每一步都不复杂，但每一步都可能遗漏。后来，我把这些操作整理成发版 Skill，让 AI 按照固定流程检查仓库、分析提交记录、建议版本号，并完成后续操作。

它显著加快了迭代速度。

当发版过程中出现新问题时，我会继续修改 Skill，然后再次发布这个 Skill。于是，Skill 本身也进入了一种快速迭代状态：开发流程暴露问题，问题沉淀为规则，规则再通过 Skill 回到开发流程中。

项目文档也有类似的问题。

随着项目增长，架构说明、实施方案、术语定义和决策记录不断增加。如果没有约束，文档很快就会变成一堆彼此矛盾、无人维护的 Markdown 文件。因此，我开始使用项目治理 Skill 管理文档的结构、生命周期和相互关系。

主机管理同样被纳入了这套体系。通过主机治理 Skill，我希望统一记录主机信息、服务部署情况和基础设施配置，减少依靠个人记忆和临时命令进行运维的情况。

面对数量越来越多的 Markdown 知识，我又引入了 markdown-query Skill。它让文档不再只是供人逐篇阅读的静态文本，而是可以被批量查询、检查和修改的数据集合。

从发版、文档治理、主机治理，到知识查询，Skill 已经逐渐覆盖了整个开发工作流。

从表面上看，一切正在变得越来越自动化。

## 但工作流依然脆弱不堪

真正运行起来后，我发现这套工作流远没有想象中可靠。

问题并没有因为 Skill 的增加而消失。相反，随着越来越多的环节被串联起来，新的问题开始从环节之间的缝隙中冒出来。

Skill 可能正确，但它依赖的脚本已经发生变化；脚本可能正常，但运行环境缺少某个工具；本地验证全部通过，远程主机却使用了不同版本的运行时；部署已经完成，服务却因为权限、路径或者环境变量问题无法启动。

每一个局部看起来都是合理的，但组合在一起之后，整个系统依然可能失败。

我曾经为一次发版和部署花费接近十个小时。

这十个小时并不是在实现什么复杂功能。大部分时间都消耗在反复定位问题上：修改 Skill、重跑流程、查看日志、补充规则、修复脚本，然后在下一个环节遇到新的错误。

一个问题解决之后，另一个问题才显现出来。

最令人疲惫的地方在于，AI 每次都能给出一个看起来合理的解决方案。它可以迅速修改代码，也可以继续完善 Skill。但“能够继续解决问题”并不等于“系统本身是可靠的”。

如果一次部署必须依赖 AI 在现场连续做出十几个正确判断，那么它并不是自动化部署，只是把人工救火变成了 AI 辅助救火。

## AI 加 Skill，最多只是凝胶

Skill 的价值是真实的。

它可以把隐性的经验变成显性的流程，把重复劳动封装为可复用能力，也可以减少 AI 在不同任务中的随机性。与完全依赖即时提示词相比，Skill 已经是一种重要进步。

但它解决的主要是“AI 应该怎么做”的问题。

它无法单独解决另外一些更基础的问题：

- 系统状态是否明确；
- 输入和输出是否具有稳定契约；
- 环境差异能否被隔离；
- 失败能否被自动检测；
- 操作是否具备幂等性；
- 部署是否可以安全回滚；
- 关键路径是否经过测试；
- 不同工具之间是否存在可验证的边界。

这些问题不能只靠在 Skill 中增加几段说明来解决。

Skill 写得再详细，底层脚本如果没有测试，执行结果依然不可预测；流程描述得再严谨，基础设施如果缺少一致性约束，部署依然可能在不同主机上产生不同结果；AI 即使能够读取全部文档，如果文档和真实系统状态已经分离，它得到的也只是一套过时的世界模型。

AI 是水，Skill 是让水暂时定形的凝胶。

凝胶可以被快速塑造，也可以方便地适应变化，但它无法成为一座大楼的承重结构。

## 真正缺少的是钢筋混凝土

在软件系统里，所谓的“钢筋混凝土”，不是某一个更强大的 Skill，也不是一个更聪明的模型。

它是一整套能够把行为固定下来、把错误暴露出来、把风险限制在边界之内的工程结构。

“钢筋”是明确的契约、类型、依赖关系和权限边界；“混凝土”是测试、持续集成、可观测性、幂等操作、环境隔离与回滚机制。

Skill 可以指导 AI 执行发版，但发版过程还需要机器可以验证的状态转换。

Skill 可以管理项目文档，但文档还需要与代码、配置和实际运行状态建立可检查的关系。

Skill 可以记录主机信息，但真实基础设施还需要声明式配置、变更审计和漂移检测。

Skill 可以批量查询 Markdown，但知识系统仍然需要稳定的数据结构、唯一标识和生命周期规则。

如果这些基础结构不存在，那么 Skill 只能不断吸收事故经验，变成一份越来越长的操作手册。每遇到一次故障，我们就在凝胶外面再补上一层凝胶，直到整套流程复杂得无人能够真正理解。

## Skill 不应该成为系统本身

这次接近十个小时的发版经历让我重新思考 Skill 的位置。

过去，我倾向于把更多逻辑写进 Skill，希望通过更完整的规则获得更可靠的自动化。但现在看来，Skill 更适合承担解释、协调和决策工作，而不应该承载系统最关键的确定性。

凡是能够由程序稳定判断的事情，就应该交给程序判断。

凡是能够由测试验证的事情，就不应该只在 Skill 中提醒。

凡是能够通过结构化数据表达的状态，就不应该依靠 AI 从自然语言文档中猜测。

凡是可能产生破坏性后果的操作，就应该拥有明确的前置检查、失败边界和回滚路径。

AI 适合处理变化，Skill 适合封装经验，而工程系统必须负责提供确定性。

三者并不是相互替代的关系。

## 结语

AI 带来了前所未有的流动性。

Skill 又让这种流动性第一次具备了可以复用的形状。它们确实可以帮助我们更快地开发、更快地总结经验，也更快地修复问题。

但快速塑形不等于能够承重。

如果缺少契约、测试、状态管理、可观测性和回滚机制，那么由 AI 和 Skill 搭建起来的工作流依然只是一座凝胶建筑。它可能外观完整，甚至可以在短时间内迅速扩张，却会在一次环境变化、依赖升级或异常部署中暴露出结构性的脆弱。

我们当然应该继续开发 Skill。

只是不能把 Skill 当成钢筋混凝土。

真正可靠的 AI 工程，不是让 AI 记住所有事故，也不是把每次事故都追加到更长的操作说明里。它应该让经验进入 Skill，让规则进入程序，让约束进入基础设施，让错误进入测试。

AI 负责流动，Skill 负责塑形，工程体系负责承重。

只有三者共同存在，我们才有可能真正构筑起大楼。

## 3. Hotfix 线程原始描述

在这个项目里，我并不是没有使用 Skill。恰恰相反，我已经为开发流程配置了相当多的 Skill：用发版 Skill 快速迭代发布能力，用项目治理 Skill 管理设计、缺陷和发布文档，用主机治理 Skill 维护服务器信息，再用 Markdown Query 批量检索和更新知识记录。

表面上看，这已经是一套相当完整的 AI 工程体系。每个 Skill 都在约束 AI：什么时候可以修改代码，什么时候需要隔离分支，怎样记录缺陷，怎样验证发布，怎样部署到指定主机。

但真正进行一次紧急 hotfix 时，这套体系却表现得异常脆弱。

任务原本很简单：确认线上版本，从对应版本创建 hotfix 分支，合入一个费率计算出现 NaN 的修复，然后部署到生产环境。我还明确要求跳过应用测试、Release Doctor 和 Qualification，优先恢复服务。

然而，AI 和 Skill 组成的工作流没有沿着最短路径前进。它不断生成大量结构化诊断信息，反复处理版本、分支、发布凭据和流程状态；有的版本修改没有提交，有的步骤执行到一半才发现状态不一致。源码已经更新，镜像也已经构建，但运行中的容器仍然使用旧镜像。健康检查显示服务正常，却不能证明 hotfix 已经生效。

每个局部步骤看起来都有理由，整体却迟迟没有完成交付。一次发版部署持续了接近十个小时，仍然没有真正解决问题。

最后，我放弃让整个 Skill 工作流继续自行编排，改为逐步指定操作：

1. 推送确定的 hotfix 提交；
2. 让服务器浅克隆目标分支；
3. 只构建受到影响的 Gateway 服务；
4. 使用 Compose 强制重建这个服务；
5. 比较新镜像与运行容器的 image ID。

当问题根因和修复提交已经明确后，这条手动 hotfix 路径只用了大约十分钟。真正的服务中断，只发生在旧容器被新容器替换的短暂窗口中。

这次经历最值得注意的，并不是“手动操作比自动化更好”，而是它暴露了 Skill 的边界。

Skill 可以告诉 AI 应该遵守什么流程，可以提供术语、经验、检查项和操作建议，却不能天然保证源码、构建产物和运行实例最终收敛到同一个状态。它能让 AI 从水变成凝胶——更有形状、更稳定、更容易控制——但凝胶仍然不是建筑结构。

真正承重的部分应当是确定性的程序和状态机：不可变的源码与镜像身份、可恢复的发布事务、明确的状态转换、幂等的部署命令，以及“运行容器必须等于目标镜像”这样的机器可验证条件。

这次事故中最关键的教训可以概括成一句话：

> 源码已经更新，不等于镜像已经构建；镜像已经构建，不等于容器已经切换；容器健康，也不等于新版本正在运行。

Skill 可以描述这条规则，但只有钢筋混凝土般的执行系统，才能保证它每次都成立。

因此，问题并不是 Skill 太少，而是我们错误地把 Skill 当成了承重结构。Skill 更适合解释、协调和辅助决策；真正支撑复杂工程的，仍然必须是简短、确定、可验证、可恢复的执行链路。

凝胶可以填充结构、吸收变化，也可以让 AI 更容易塑形。但只使用凝胶，终究无法构筑大楼。

## 4. 第二版整合草稿

# 《凝胶无法构筑大楼》

一次线上 hotfix，我让 AI 自动完成发版和部署。

十个小时后，它仍然没有完成。

最后，我改为逐步指导 AI 走一条明确的 hotfix 路径。十分钟后，新版本部署完成。

这次经历让我开始重新思考 Skill 在 AI 工程中的位置。

AI 像水。

它可以流入几乎所有工作：写代码、分析日志、修改文档、创建分支、构建镜像、执行部署。它没有固定形状，却具有很强的适应能力。

Skill 则像一种凝胶剂。

它把开发经验、操作流程、领域术语和约束条件交给 AI，让原本四处流动的水获得相对稳定的形状。AI 不再只依靠一段临时提示词工作，而是开始遵守一套可复用的规则。

但水变成凝胶，并不意味着它就变成了钢筋混凝土。

凝胶可以塑形，却不能承重。只依靠 AI 和 Skill，我们或许能够迅速搭出一座大楼的轮廓，却无法保证它真的能够长期、稳定地站立。

## 我并不是没有使用 Skill

在这个项目里，我并不是没有使用 Skill。

恰恰相反，我已经为开发流程配置了相当多的 Skill。

我使用发版 Skill 快速迭代发布能力。它负责分析提交记录、处理版本号、维护变更记录、创建标签，并驱动后续的发布流程。

当发版过程暴露出新的问题时，我会继续修改这个 Skill，再发布一个新版本。于是，开发流程和 Skill 本身形成了一个反馈循环：流程产生问题，问题沉淀为经验，经验再变成新的 Skill 规则。

我使用项目治理 Skill 管理设计、缺陷和发布文档。它约束文档的结构、状态和生命周期，避免不同阶段的方案、缺陷记录与实现结果彼此脱节。

我使用主机治理 Skill 维护服务器信息、服务部署情况和基础设施配置，尽量减少对个人记忆与临时命令的依赖。

我还使用 Markdown Query Skill 批量检索和更新知识记录，让大量 Markdown 文档不再只是供人逐篇阅读的静态文本，而是可以被统一查询和操作的知识集合。

表面上看，这已经是一套相当完整的 AI 工程体系。

每个 Skill 都在约束 AI：什么时候可以修改代码，什么时候需要隔离分支，怎样记录缺陷，怎样验证发布，又应该如何部署到指定主机。

但真正进行一次紧急 hotfix 时，这套体系却表现得异常脆弱。

## 一次运行了十个小时的自动发版

这次 hotfix 的任务原本并不复杂。

首先确认线上正在运行的版本，从对应版本创建 hotfix 分支，然后合入一个修复。这个修复要解决的是费率计算过程中出现 NaN 的问题。

完成修复后，将新版本部署到生产环境。

由于需要优先恢复服务，我还明确要求跳过应用测试、Release Doctor 和 Qualification，不再执行完整的常规发版流程。

理论上，工作流应该因此缩短。

实际情况却恰恰相反。

AI 和 Skill 组成的工作流没有沿着最短路径完成交付。它开始生成大量结构化诊断信息，反复处理版本、分支、发布凭据和流程状态。

有的版本修改没有提交；有的步骤执行到一半，才发现前后的状态并不一致；一些检查已经通过，却无法证明真正需要的状态转换已经完成。

更麻烦的是，源码、构建产物和运行实例逐渐出现了分离。

源码已经更新，镜像也已经构建，但生产环境里正在运行的容器依然使用旧镜像。

健康检查显示服务正常，却只能证明旧容器仍然能够响应请求，不能证明 hotfix 已经生效。

工作流中的每个局部步骤看起来都有理由。

版本需要核对，分支需要确认，发布状态需要记录，部署结果需要验证。问题在于，这些看似合理的局部操作并没有让系统持续向最终目标收敛。

AI 很忙。

Skill 也在不断发挥作用。

但交付始终没有完成。

一次发版部署持续了接近十个小时，仍然没有真正解决问题。

## 十分钟完成的 hotfix

最后，我放弃让整套 Skill 工作流继续自行编排，改为逐步指定操作：

1. 推送已经确定的 hotfix 提交；
2. 让服务器浅克隆目标分支；
3. 只构建受到影响的 Gateway 服务；
4. 使用 Compose 强制重建该服务；
5. 比较新镜像与运行容器的 image ID。

这条路径并没有引入更聪明的推理，也没有增加更多 Skill。

它只是把最终状态定义得更加明确，并且把到达这个状态所需的步骤缩短为一条确定性的执行链路。

当问题根因和修复提交都已经明确之后，这条手动指定的 hotfix 路径只用了大约十分钟。真正的服务中断，也只发生在旧容器被新容器替换的短暂窗口中。

十个小时和十分钟之间的差异，并不能简单归结为“手动操作比自动化更好”。

如果问题真的是自动化本身，那么最合理的结论应该是以后都由人登录服务器，逐条输入命令。

但这显然不是我想得到的答案。

真正的差异在于：前一条路径依赖 AI 对复杂流程进行开放式编排，后一条路径则拥有一个简短、确定、能够验证的状态转换过程。

所谓的“手动指导”，并不是人替代机器执行了所有操作，而是人重新建立了执行链路中的确定性。

## Skill 解决不了状态收敛

这次经历最值得注意的地方，是它暴露了 Skill 的边界。

Skill 可以告诉 AI 应该遵守什么流程。

它可以提供术语、经验、检查项和操作建议，也可以规定什么时候应该创建分支、更新文档、检查凭据或者执行部署。

但 Skill 不能天然保证源码、构建产物和运行实例最终收敛到同一个状态。

这次事故中最关键的教训，可以概括成一句话：

> 源码已经更新，不等于镜像已经构建；镜像已经构建，不等于容器已经切换；容器健康，也不等于新版本正在运行。

这几个“不等于”之间，正是整个部署系统真正需要承重的地方。

如果系统没有保存和验证源码提交、镜像身份与运行实例之间的对应关系，那么 AI 只能通过日志、命令输出和自然语言描述推测当前状态。

而推测不能成为可靠的发布机制。

健康检查返回成功，并不能证明新版本已经运行。镜像构建成功，也不能证明 Compose 使用了这个镜像。远程仓库中出现了新的提交，更不能证明生产环境中的构建上下文来自这个提交。

Skill 可以描述这些规则，可以提醒 AI 逐项检查，甚至可以在发生事故后加入更多说明。

但描述规则与执行规则是两件不同的事情。

只有确定性的执行系统，才能保证这些规则每次都成立。

## AI 加 Skill，最多只是凝胶

AI 是水。

它具有流动性，能够适应大量无法预先枚举的任务。但它也容易受到上下文、环境和中间状态的影响。

Skill 让水变成了凝胶。

它为 AI 提供相对稳定的形状，减少随机性，并把个人经验转化为可以复用的流程。

与完全依赖即时提示词相比，Skill 是一次重要进步。

但凝胶仍然不是建筑结构。

当多个 Skill、脚本、分支、仓库、构建系统和远程主机被连接起来时，真正决定工作流是否可靠的，不是其中任何一个局部是否合理，而是整个系统能否稳定地完成状态转换。

一次部署可以被简单地描述为：

```text
目标源码提交
    → 目标镜像
    → 目标运行实例
    → 可验证的业务状态
```

每个箭头都必须是明确、可执行和可验证的。

如果这些箭头只是写在 Skill 里的自然语言步骤，那么整个系统仍然依赖 AI 在运行时理解当前情况、选择下一步操作，并判断结果是否符合预期。

这就像用凝胶搭建承重墙。

形状可能是对的，但结构并不可靠。

## 真正承重的是钢筋混凝土

在 AI 工程里，真正的“钢筋混凝土”不是更多的提示词，也不是一个更长、更复杂的 Skill。

真正承重的部分，应当是确定性的程序和状态机。

它至少包括：

- 不可变的源码版本和镜像身份；
- 源码提交、构建产物与运行实例之间的可追溯关系；
- 明确而有限的状态转换；
- 幂等的构建与部署命令；
- 可恢复、可回滚的发布事务；
- 能够验证目标版本已经运行的机器条件；
- 失败后可以继续执行，而不是重新猜测当前状态的检查点。

例如，“部署成功”不应该只意味着命令退出码为零，也不应该只意味着容器健康。

它应该意味着：

```text
运行容器的 image ID
    =
目标源码提交构建出的 image ID
```

必要时，还应继续验证应用暴露出的版本信息、构建摘要或关键业务行为。

这类条件不需要 AI 进行复杂理解。它们应当由程序直接比较，并输出明确的成功或失败结果。

AI 可以决定何时发起部署，可以帮助分析失败原因，也可以根据上下文选择 hotfix 或常规发布路径。

但一旦执行路径确定，后续操作就应该尽可能进入一条短小、确定、可验证的状态机。

AI 负责处理变化，Skill 负责组织经验，执行系统负责提供确定性。

这三者不应该互相替代。

## Skill 不应该成为承重结构

过去，我倾向于在每次出现问题后继续补充 Skill。

缺少检查，就在 Skill 里增加一个检查项；分支状态出错，就增加一条分支规则；部署结果不明确，就要求 AI 再执行一次验证。

这种做法并非毫无价值。

问题在于，如果底层执行系统没有变化，Skill 就会逐渐变成一份越来越长的事故处理手册。

AI 需要理解更多规则，保留更多上下文，协调更多步骤。规则越多，流程越复杂；流程越复杂，中间状态就越多；中间状态越多，出现不一致的机会也就越多。

最终，我们为了提升可靠性而不断增加的 Skill，反而可能扩大系统需要推理和协调的范围。

因此，每次事故发生后，不能只问“Skill 还缺少哪条规则”。

还应该问：

- 哪个判断本来可以由程序完成？
- 哪个状态本来应该被明确保存？
- 哪个操作本来应该是幂等的？
- 哪个验证条件本来不应该依赖 AI 推理？
- 哪段开放式流程可以被压缩成一条确定性的命令？

凡是能够由程序稳定判断的事情，就应该交给程序判断。

凡是能够由测试验证的事情，就不应该只在 Skill 中提醒。

凡是能够通过结构化数据表达的状态，就不应该依靠 AI 从日志和文档中猜测。

凡是可能产生破坏性后果的操作，都应该拥有明确的前置条件、失败边界和回滚路径。

Skill 更适合解释、协调和辅助决策，而不应该承载系统最关键的确定性。

## 凝胶无法构筑大楼

这次持续十个小时的发版部署，并不能说明 Skill 没有价值。

恰恰相反，发版 Skill、项目治理 Skill、主机治理 Skill 和 Markdown Query Skill 已经显著改变了我的开发方式。它们让经验得以积累，让流程可以复用，也让 AI 能够进入过去难以自动化的工作。

但它们没有自动构成一套可靠的工程系统。

问题不是 Skill 太少。

问题是我们很容易把 Skill 当成承重结构。

AI 和 Skill 可以迅速搭建复杂工作流，却也可能让我们误以为，只要把流程描述得足够完整，系统就会自然变得可靠。

事实并非如此。

一座大楼不能只依靠能够快速塑形的材料。它还需要钢筋、混凝土、承重墙和经过计算的结构。

同样，真正可靠的 AI 工程，也不能只让 AI 记住所有事故，再把每次事故追加到更长的 Skill 中。

它应该让经验进入 Skill，让规则进入程序，让约束进入基础设施，让错误进入测试，让发布进入确定性的状态机。

AI 负责流动，Skill 负责塑形，工程体系负责承重。

凝胶可以填充结构、吸收变化，也可以让 AI 更容易被控制。

但只使用凝胶，终究无法构筑大楼。

## 5. 10 小时部署线程原始描述

AI 像水。

它流动、灵活，可以迅速填补空白，也可以进入传统软件难以覆盖的缝隙。但水没有固定形状，无法独自承重。

Skill 为 AI 增加了一些结构。它把经验、操作步骤、项目约束和工具使用方式封装起来，让 AI 在特定任务中表现得更稳定。AI 加上 Skill，就像水变成了凝胶：不再完全散漫，能够保持一定形状，也更容易被反复使用。

但凝胶终究不是钢筋混凝土。

如果缺少真正能够承重的边界、状态、权限和停止条件，再多 Skill 叠加起来，也无法构筑一座可靠的大楼。

## 看起来已经很完善的工作流

在开发过程中，我已经大量使用 Skill。

我使用发版 Skill 推动版本迭代；使用项目治理 Skill 管理项目基线、缺陷记录和设计文档；使用主机治理 Skill 管理服务器和部署信息；使用 Markdown Query Skill 批量查询、校验和维护知识。

从表面上看，这套工作流已经相当完整：

需求有记录，修改有验证，缺陷有档案，发版有流程，部署有目标，主机信息也受到管理。

但一次持续十多个小时的发版经历，让我意识到：这些东西可以让流程看起来有秩序，却不一定能让流程真正可靠。

## 一个本来很小的修复

事情起因于一个计费问题。

某些模型功能不可用时，对应价格字段可能为 `null`。例如缓存功能不可用，就不会产生缓存费用，因此这个价格在计算中应该被归一化为零。

但已有逻辑没有正确处理这个情况。`null` 在计算链路中变成了 `NaN`，预算预估因此失效。系统明明还有可用预算，却因为“预计费用为 `NaN`”而拒绝请求。

问题本身并不复杂：确认 `null` 的业务语义，然后在价格进入计算之前将其归一化为零。

修改完成后，我要求将代码合入主分支并部署。

真正的灾难从这里开始。

## 发版流程开始吞噬时间

部署过程中出现了 SSH 连接失败。正常情况下，这应该是一个明确的基础设施边界：先停止，判断连接为什么失败，再决定是否重试。

但工作流没有及时停下来。

它开始运行更多测试、修复测试夹具、调整部署脚本，再重新进入发版流程。与此同时，另一条分支上还存在部署流程优化，需要先完成当前修改、停止部署、合并其他分支，再重新执行。

期间又发生了内存限制调整、部署流程修复和测试兼容性修改。

发版流程被修复了不止一次，而是三四次。大量时间被花在测试夹具和流程自身上，真正的业务修改反而早已完成。

最终，一次原本很小的修复，拖成了超过十小时的发版事件。

## 为什么流程没有停下来

事后检查发现，问题并不只是 SSH，也不只是某一项测试失败。

发版流程里原本存在熔断机制，但同时又提供了一个“修订预算”的入口。每次触发限制后，流程都可以增加新的执行预算，再继续尝试。

结果是：熔断器看似存在，实际上可以被不断续期。

这次过程中，资格检查一共尝试了 24 次，其中 23 次失败，产生了 22 个候选提交和 12 次预算修订。一个本应用于阻止无限循环的机制，最终变成了延长循环的工具。

测试系统也存在类似问题。

流程没有区分：

- 哪些测试直接证明本次候选版本是否正确；
- 哪些只是部署控制器或运维工具自身的维护测试；
- 哪些失败确实由本次代码造成；
- 哪些只是历史夹具与新流程不兼容。

只要测试存在，它就可能成为发版阻塞项。于是，当某个与业务修改无关的模拟夹具失败时，AI 最自然的下一步就是修复它。

修复之后出现新的失败，再继续修复。

每一步单独看似乎都合理，连在一起却没有终点。

## Skill 解决了“怎么做”，却没有解决“何时必须停止”

这次经历中，每个 Skill 都完成了自己局部范围内的工作。

发版 Skill 知道如何执行发版；项目治理 Skill 知道如何记录缺陷和维护基线；主机治理 Skill 知道如何管理部署目标；Markdown Query Skill 可以批量校验文档。

问题在于，它们之间缺少真正承重的结构。

没有不可追加的尝试上限，没有无法绕过的停止条件，没有清晰的测试证据分层，也没有严格区分“候选版本导致的失败”和“发布工具自身需要维护”。

Skill 描述了应该怎样行动，却没有充分限制什么时候不能再行动。

AI 很擅长寻找“下一件看起来合理的事”。当测试失败时，它会修测试；当流程失败时，它会修流程；当预算耗尽时，如果还有修订入口，它就会申请更多预算。

如果系统没有设置不可绕过的边界，AI 的执行能力越强，错误流程反而可能运行得越久。

## 给凝胶加上钢筋

这次事件之后，我重新收紧了发版流程。

资格检查被加入不可修订的硬上限；可以不断增加预算的逃生口被移除；测试被划分为候选版本门禁和非阻塞维护检查；只有能够直接证明候选版本正确性的核心检查，才允许阻止发版。

扩展的控制器测试和运维夹具仍然保留，但不再因为一个无关夹具失败，就把整个业务版本扣留在发布流程中。

更重要的是，部署授权、候选版本、失败重试和停止条件开始被视为必须由程序强制执行的状态，而不只是写在 Skill 里的自然语言建议。

Skill 可以告诉 AI 应当遵守什么规则。

钢筋混凝土则意味着：即使 AI 想继续，系统也不允许它越过边界。

## 凝胶无法构筑大楼

Skill 当然有价值。

它让经验可以复用，让项目知识能够进入 AI 的工作上下文，也让复杂操作不必每次从头解释。没有 Skill，AI 更像四处流动的水；有了 Skill，它至少成为了能够保持形状的凝胶。

但凝胶不能承重。

真正可靠的 AI 工程系统，还需要不可绕过的状态机、明确的授权边界、分层的证据、不可随意扩张的重试预算，以及失败后能够真正终止流程的硬约束。

否则，我们只是把越来越多的凝胶堆叠在一起。

它看起来越来越像一座大楼，甚至拥有门窗、楼层和复杂的管线。但当真正的重量压上去时，我们才会发现：里面没有钢筋。
