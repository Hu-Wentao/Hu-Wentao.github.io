在 AI 辅助开发中，Token 消耗量很容易被误认为工作量，工作量又很容易被误认为工程价值。一个 Agent 可以读取整个代码库、追踪所有依赖、列出几十条风险，再生成一份结构完整的报告。这个过程会消耗大量上下文和推理资源，却不一定让产品向前推进一步。

这并不意味着架构审查、安全审查或性能分析没有价值。问题在于：当任务没有明确问题、范围和验收目标时，这些活动很容易从工程手段变成 Token 消耗器。

为此，我实现了 `burn-tokens-fast` Skill。它维护一份“高 Token 消耗、低日常收益”的开发活动清单，帮助使用者识别哪些请求看起来专业而全面，实际却可能缺少可交付结果。

它的核心可以概括成一句话：

> 不评价一项工程活动是否永远有用，而是记录它在缺少具体目标时，如何消耗大量 Token 却只产生有限收益。

## Token 消耗不等于任务价值

适合大量消耗 Token 的任务通常有几个共同特征：

- 范围覆盖整个项目，而不是一个已知问题；
- 需要读取大量代码、配置、文档和外部资料；
- 需要跨文件重建关系，或者比较许多可能方案；
- 产出以报告、建议和大规模 diff 为主；
- 没有与任务对应的性能指标、漏洞、兼容目标或产品需求。

这些特征会让 Agent 持续扩大上下文。它需要先建立项目全貌，再分析每个局部，随后处理例外、误报和兼容问题。任务越强调“全面”“所有”“整个项目”，Token 消耗通常越高。

然而，工程价值取决于任务是否解决了真实问题。一次性能审查如果围绕明确的延迟指标展开，可以直接改善用户体验；如果没有慢请求、基准数据或受影响的用户路径，同样的审查可能只会得到一组理论上的优化建议。

`burn-tokens-fast` 记录的不是“无用活动”，而是“缺少目标时容易低收益的活动”。

## 用三个字段记录一项活动

清单中的每项活动都使用相同结构：

- **活动内容**：Agent 实际需要检查、分析或修改什么；
- **为何消耗 Token**：任务在哪些地方扩大上下文和推理范围；
- **为何日常收益有限**：缺少什么前提时，产出难以转化为实际结果。

固定结构让清单不只是几个调侃式标题。使用者可以看到一项活动为什么昂贵，以及需要补充什么目标才能让它重新具有工程价值。

例如，“全项目性能审查”的问题不在于性能分析本身，而在于没有测量对象。如果请求补充了性能基线、目标阈值和受影响路径，它就不再只是 Token 消耗活动，而会成为范围清楚的优化任务。

## 当前收录的活动

`burn-tokens-fast` 当前收录五类活动。

### 更新项目上游依赖

这项活动会检查直接和间接依赖，阅读版本说明与变更记录，更新版本和 lock 文件，迁移受影响的 API，再运行兼容性测试。

它需要处理多个生态系统的信息：依赖关系、版本约束、源码变化、弃用说明、迁移策略和测试失败都会进入上下文。如果项目没有需要的新特性、已知漏洞或兼容性问题，全面更新往往只会制造额外的迁移与评审工作。

### 进行安全审查

一次宽泛的安全审查可能覆盖架构、依赖、身份认证、权限控制、密钥、配置、持续集成与持续交付（CI/CD）、输入处理、数据流和威胁边界。

为了判断一个问题是否真实存在，Agent 不仅要找到可疑代码，还要追踪它的调用条件、保护措施和外部边界，并过滤静态规则产生的误报。如果没有明确的威胁模型、审查范围、合规要求或修复目标，最终产物通常是一份很长的风险报告。

### 全项目架构审查

全项目架构审查要求 Agent 检查所有模块、边界、依赖方向、控制流、数据流、部署组件和横切关注点，然后重建架构并提出结构调整方案。

这类任务天然需要读取大部分代码库。每条建议还需要比较替代方案，并说明它与现有实现之间的关系。如果项目没有明确的扩展性、可维护性、职责归属或交付问题，审查很容易停留在“可以重新分层”“可以降低耦合”这类宽泛结论。

### 全项目性能审查

全项目性能审查同时关注应用逻辑、数据库、网络、渲染、并发、内存和构建路径，并可能要求建立基准和提出优化方案。

它会引入调用链、查询、执行剖析、运行轨迹、复杂度和回归风险等大量材料。没有可测量的瓶颈、性能目标或受影响的用户路径时，Agent 只能推测哪些部分“可能更快”，却无法证明修改会改善可观察行为。

### 全量代码风格统一

这项活动会检查并重写整个仓库的命名、格式、文件组织、抽象、注释、错误处理模式和语言惯用法，随后运行格式化、静态检查和测试。

它会产生大量跨文件 diff，也需要反复判断什么才算“一致”。如果现有代码已经可读，项目又没有可自动执行的规范，这类修改主要带来外观变化，并增加代码评审、分支合并和行为回归的成本。

## 查看清单不会自动执行任务

调用这个 Skill 时，Agent 默认只返回活动清单。下面的提示只要求查看当前记录：

```text
使用 $burn-tokens-fast 查看适合快速消耗 Token 的开发活动清单。
```

查看一项活动的原因时，可以进一步指定条目：

```text
使用 $burn-tokens-fast 说明为什么全项目架构审查会消耗大量 Token，
以及它在什么情况下收益有限。
```

Skill 不会因为使用者查看清单，就自动开始更新依赖、扫描安全问题或重写代码风格。执行某项活动需要同时满足两个条件：

1. 使用者明确要求执行具体活动；
2. 使用者提供任务范围。

例如，下面的请求同时给出了活动和范围：

```text
使用 $burn-tokens-fast，对当前仓库的 API 服务执行全项目性能审查。
范围包括请求链路和数据库查询，不检查前端构建性能。
```

这条边界避免“告诉我哪些任务耗 Token”被解释成“现在就替我运行所有任务”。它也迫使执行请求至少说明检查对象，减少 Agent 自行扩张任务范围的机会。

## 为清单增加活动

当使用者明确提供新活动时，Skill 会按现有三个字段记录它。新增条目需要回答：

1. Agent 具体要做什么？
2. 哪些材料或推理过程会大量消耗 Token？
3. 缺少哪些目标时，这项活动的日常收益有限？

Skill 不会自行发明并追加活动。这项限制让清单保持人为审核：Agent 可以解释条目，但哪些活动值得收录，仍由维护者决定。

一个合适的候选不应只是“任务很长”。它还应该具有明显的上下文扩张机制，并且能够指出让任务重新变得有价值的具体条件。例如，安全审查需要威胁模型或合规边界，性能审查需要基线和目标，依赖更新需要漏洞、特性或兼容性需求。

## 它适合解决什么问题

`burn-tokens-fast` 不是性能分析器、安全扫描器或依赖升级工具。它不实现这些活动，也不衡量一次请求实际使用了多少 Token。它提供的是一份可复用的任务分类，用于识别宽泛工程请求中的投入产出问题。

这份清单可以用于：

- 在启动大范围任务前检查请求是否缺少目标；
- 讨论 Agent 工作量与工程价值的差异；
- 为 Token 密集型任务补充范围和验收条件；
- 记录经过人工审核的低日常收益活动。

当一项活动拥有具体问题、明确范围和可验证结果时，不应因为它出现在清单中就拒绝执行。清单描述的是活动在特定条件下的风险，不是对工程实践的永久评价。

## 结语

AI 辅助开发降低了读取代码、生成建议和批量修改的成本，也让“做很多事情”变得比“确认该做什么”更容易。一个覆盖整个项目的任务可以迅速消耗大量 Token，却可能没有对应的产品变化、故障修复或可验证指标。

`burn-tokens-fast` 用一份很小的清单保存这种差异。它记录活动、Token 消耗机制和收益边界，查看时只展示信息，执行时要求明确授权与范围，新增条目时保留人工审核。

真正需要避免的不是大任务，而是没有问题定义、没有任务边界，也没有完成标准的大任务。
