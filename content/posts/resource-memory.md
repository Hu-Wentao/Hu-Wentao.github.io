我们每天都会遇到值得保留的东西：一个设计漂亮的开源项目，一套可以复用的工作流，一篇解释某项政策限制的文章，或者一段暂时用不上、以后却可能解决问题的知识。

传统做法是把它们放进浏览器书签、稍后阅读、笔记软件或 GitHub Stars。收藏动作很轻，重新找到它们却很难。几个月后开始另一个项目时，我们往往只记得“好像见过类似方案”，却想不起标题、关键词和存放位置。

对 AI Agent 来说，这个问题更加直接：书签存在，并不意味着 AI 知道它存在。Agent 进入一个新项目后，只能依据当前仓库、当前对话和临时搜索结果工作。过去积累的资源没有进入它的发现路径，就等于没有形成可以复用的记忆。

为此，我实现了 `recall-resources` Skill，以及为它提供数据和检索能力的 `resource-memory` 项目。它要解决的不是“怎样收藏更多链接”，而是：

> 当未来的任务与某个旧资源可能相关时，让 AI 主动找到它，并说明为什么相关、有哪些限制、是否需要重新核验。

## 从书签变成可召回的资源

假设某天看到一篇介绍“中国身份如何创建 Stripe 账户”的文章。此刻可能没有支付项目，只是觉得以后会有用，于是把它收藏起来。

几个月后，另一个项目需要选择支付渠道。普通书签系统不会参与这次技术讨论；如果已经把文章保存进 `resource-memory`，Agent 可以将当前问题扩展为“支付渠道、支付网关、Stripe、中国身份、主体限制”等相关语义，召回这篇文章，并给出类似提示：

> 资源库里有一篇讨论中国身份条件下使用 Stripe 的实践文章，可能帮助评估 Stripe 的可行性。但它属于经验资料，采用前需要重新核验当前地区、主体和合规政策。

这与简单搜索 `Stripe` 不同。真正需要保存的是“它能解决什么问题”和“什么时候应该想到它”。因此，一条资源记录不只包含标题和 URL，还包含以下内容：

```md
## RES-20260804-XXXXXXXXXX — 中国身份创建 Stripe 的实践文章

Type: article
URL: https://example.com/article
Captured At: 2026-08-04
Review Status: unverified

### Summary

帮助中国团队评估 Stripe 作为线上支付渠道的可行性。

### Use When

- 项目需要选择线上支付渠道
- 中国身份或企业主体可能影响服务注册

### Constraints

- 文章属于经验资料，不代表服务商当前官方政策
- 采用前需要重新核验地区、主体和合规要求
```

`Summary` 描述资源的可复用价值，`Use When` 保存未来任务中的触发信号，`Constraints` 则防止 Agent 因为检索到了资源，就忽略它的适用边界。

## 日常使用不是填写表格

结构化记录不意味着每次收藏都要手工填写字段。安装 Skill 后，可以在任意项目或对话里直接说：

```text
收藏这个资源：https://example.com/article
它主要用于中国团队评估 Stripe 注册和支付接入。
```

Agent 会读取能够访问的来源，提取标题、资源类型、摘要、适用场景和限制，生成稳定资源 ID，写入 Markdown，然后增量更新检索索引。

也可以把判断直接告诉它：

```text
收藏这个 GitHub 项目，适用于 Flutter 自动化测试。

收藏这篇文章，但注明政策可能已经过期。

把这个工作流收藏起来，以后做文章转视频时提醒我。
```

外部资料默认标记为 `unverified`。如果页面无法访问，而用户也没有提供足够信息，Skill 不会为了完成收藏而编造摘要、URL 或适用场景。

需要脚本化时，也可以直接调用 CLI：

```bash
uv run resource-memory add \
  --title "中国身份创建 Stripe 的实践文章" \
  --type article \
  --url "https://example.com/article" \
  --summary "帮助中国团队评估 Stripe 支付接入可行性" \
  --use-when "项目需要选择线上支付渠道" \
  --constraint "使用前重新核验当前地区与主体政策"

uv run resource-memory index --load-model
```

写入前会检查现有目录是否合法，并拒绝重复 URL、重复 ID 和会破坏记录边界的内容。写入使用原子替换；任何一步失败，都不会留下半条资源记录。

## 关键词搜索与语义搜索各自负责什么

只做向量检索，会让结果看起来“很智能”，却难以解释精确名称、URL 和稳定概念为什么命中。只做关键词搜索，又会错过“支付渠道”和“Stripe 注册文章”之间没有直接共享字面的关联。

`resource-memory` 因此组合了两条召回路径：

| 路径 | 作用 |
| --- | --- |
| SQLite FTS5 trigram | 查找标题、摘要、适用场景中的精确词语和中文子串 |
| 本机 Embedding | 发现不同措辞之间可能存在的语义关联 |

当前默认通过 LM Studio 的 OpenAI 兼容接口调用本机 `text-embedding-nomic-embed-text-v1.5`，索引文档和搜索问题分别使用 `search_document:` 与 `search_query:` 任务前缀。两条路径的结果通过排名融合，而不是把不兼容的分数直接相加。

例如，在临时测试库中保存 Stripe 文章和一个无关的“文章转视频工作流”后，查询“中国团队如何接入在线支付渠道”，Stripe 文章同时取得关键词排名第一和语义排名第一；无关工作流只有较低的语义候选，不会因为共享了“项目”“流程”等宽泛词语而获得关键词加权。

向量相似度仍然只是发现证据，不是适用性结论。最终是否推荐，要由 Agent 阅读资源摘要、限制和当前项目约束后判断。

## Markdown 是事实源，SQLite 只是缓存

很多知识库从一开始就把数据库或向量库当作主要存储。这样查询很方便，但几年后更换模型、索引引擎或应用时，原始知识也容易被困在某个实现里。

`resource-memory` 采用相反的权威边界：

- Markdown 保存资源身份、来源、摘要、适用场景和限制；
- Git 保存可审查的修改历史；
- SQLite 保存全文索引和向量；
- Embedding 模型只负责生成可重建的派生数据；
- `recall-resources` Skill 负责决定何时搜索、怎样解释结果。

索引会记录源内容摘要、模型标识、向量维度和 Schema 版本。Markdown、概念目录或模型发生变化后，旧索引会被判定为过期；重新运行 `index` 即可恢复，不需要迁移或重写收藏内容。

这条边界也限制了 Skill 的权限。找到某个开源项目，不等于授权安装它；找到某个支付服务，不等于授权注册、购买或接入；找到一篇实践文章，也不能把文章中的历史经验当成当前官方政策。

## 与项目治理结合：共享事实，保留项目判断

一个值得继续发展的方向，是把资源记忆与项目治理中的开源项目评估结合起来。

开源项目本身的许可证、维护活跃度、核心能力、架构特点、官方文档和已知风险，与“它是否适合当前项目”是两类不同事实。前者可以跨项目复用，后者依赖当前项目的需求、技术栈、部署方式、数据边界和兼容承诺。

更合理的分层是：

| 权威位置 | 保存内容 |
| --- | --- |
| `resource-memory` | 开源项目自身的通用评估、上游版本、许可证、能力与风险 |
| 当前项目 | 对共享评估的稳定引用、匹配程度、项目特有约束、缺口和采用建议 |

这样，三个项目评估同一个开源库时，不必复制三份上游资料；而某个项目得出的“建议采用”，也不会污染其他项目的判断。共享评估只提供证据，是否试用、采用或拒绝，仍由每个项目自己的治理记录负责。

这个集成还需要解决评估版本固定、共享记录更新、离线可追溯和并发写入等问题，因此目前仍是后续方向，不属于首期已经交付的行为。

## 结语

个人知识管理最容易积累的是链接，最难积累的是“这个东西以后会在什么问题里有用”。如果缺少这层语义，收藏越多，重新发现的成本反而越高。

`recall-resources` 尝试把收藏动作变成一种面向未来 Agent 的记忆编码：记录资源是什么，也记录它解决什么问题、在什么条件下适用、有哪些不能忽略的限制。全文检索保证精确发现，Embedding 帮助跨越措辞差异，Markdown 和 Git 则保证这些知识不依赖某个向量数据库才能存在。

真正有价值的结果不是 AI 能回答“我收藏过什么”，而是在新项目遇到问题时，它能够及时说出：

> 你以前见过一个可能相关的东西。这里是它与当前任务的关联，以及在采用前仍需确认的边界。
