让 Agent 写一篇语句通顺的技术文档并不困难。真正困难的是让文档同时满足几个条件：命令确实可执行，前置条件没有遗漏，读者能快速找到下一步，术语在整篇文档中保持一致，链接和示例不会误导使用者。

这些问题不能只靠“润色一下”解决。文字可以很流畅，却仍然隐藏错误的参数；结构可以很完整，却没有告诉读者操作会改变什么状态；示例可以看起来真实，却包含未经验证的输出。

`write-technical-docs` Skill 为此提供了一套面向开发者文档的写作与审校流程。它以 [Google Developer Documentation Style Guide](https://developers.google.com/style) 为编辑基础，但不会用通用风格规则覆盖项目事实、用户要求或本地文档约定。

它的核心可以概括成一句话：

> 先确认技术事实与任务边界，再用最少且足够的结构，把它们组织成读者能够执行和验证的文档。

## 它解决的不是“文笔”问题

技术文档至少同时承担两种职责：准确描述系统，并帮助读者完成任务。只优化其中一项，文档仍然可能不可用。

例如，一段安装说明可以没有语法错误，也可以使用统一的标题和代码块，但如果它漏掉了工作目录、权限要求或必要的环境变量，读者仍然无法完成安装。反过来，一份记录了所有技术细节的说明，如果按实现历史堆叠信息，也会迫使读者从大量背景中自行推断操作顺序。

`write-technical-docs` 因此把技术正确性放在编辑质量之前。它要求 Agent 不得编造命令、参数、API 行为、兼容性结论、预期输出或产品名称。无法从现有证据确认的事实，应该被明确标记或交还给使用者确认，而不是用自然流畅的句子填补空白。

在事实成立之后，Skill 才继续处理结构、语言、格式和可访问性。这条顺序避免了一个常见误区：把“读起来像文档”误认为“已经可以交付”。

## 规则有明确的优先级

通用写作规范不可能了解每个项目的术语、模板和兼容承诺。`write-technical-docs` 使用一条明确的规则优先级来处理冲突：

1. 先遵守用户要求、目标项目的术语、模板、格式和检查规则；
2. 项目没有规定时，再应用 Skill 与 Google 技术写作指南；
3. 修改既有文档时，保留有意形成的局部一致性；
4. 只有不同解释会实质改变受众、含义或结构时，才请求使用者决定。

这意味着 Skill 不会为了机械符合一条外部规范，把一个项目中约定俗成的名词全部替换掉，也不会修改必须保持原样的 API 名称和代码标识符。准确性与读者理解始终高于机械合规。

同一原则也适用于中文文档。Skill 会继续使用任务优先、渐进披露、可访问性和链接规范，但不会把美式英语的语法、拼写和标点规则强加到中文正文中。

## 按任务加载写作规范

Skill 没有把全部写作规则塞进一份很长的主说明。它将详细规范拆成四份 reference，并根据当前任务按需加载：

| 参考文件 | 处理的问题 |
| --- | --- |
| `voice-and-language.md` | 语气、句子清晰度、包容性、国际化和可访问性 |
| `structure-and-formatting.md` | 页面结构、标题、段落、列表、步骤、表格和提示信息 |
| `code-ui-and-links.md` | 行内代码、代码示例、命令、占位符、界面操作和链接 |
| `wording-and-naming.md` | 大小写、缩写、数字、日期、文件名、示例数据和产品名称 |

如果任务只是检查链接和命令格式，Agent 不必加载所有语言规则；如果要起草或审校一篇完整文档，则读取前四份 reference。只有需要查询 Google 原始规则或核对当前产品名称时，才继续读取 `source-index.md` 并访问权威来源。

这种组织方式既减少无关上下文，也让主 `SKILL.md` 保持在工作流层面。Agent 先知道应该如何判断，再在当前任务需要时读取具体规则。

~~~text
用户目标 + 项目规则
        ↓
     SKILL.md
        ↓ 当前文档实际需要
语言 / 结构 / 代码与链接 / 命名规范
        ↓ 必要时查询
Google 原始指南或产品权威来源
~~~

## 写作从读者任务开始

创建或重写文档时，Skill 首先识别六项信息：读者是谁、读者要完成什么、文档属于哪种类型、默认具备哪些知识、操作有哪些前置条件，以及技术结论由什么证据支持。

随后，Agent 检查相邻文档和项目规则，再决定标题、术语与格式。正文按照读者需要信息的顺序展开，而不是按照功能的开发顺序或作者的思考过程排列：

1. 在开头说明读者能够学到什么或完成什么；
2. 在操作之前列出必要的前置条件与限制；
3. 先给出最常见的执行路径，再补充替代方案和边界情况；
4. 将解释、命令、预期结果和验证方式放在对应步骤附近；
5. 删除重复内容、填充句、未经支持的承诺和与任务无关的脚手架。

当文档包含操作流程时，每个步骤只承担一个主要动作。命令使用带语言标识的代码块，命令与输出分开呈现，所有占位符都在读者需要替换之前解释。可选步骤会明确标记为“可选”，破坏性操作、权限要求和外部状态变化也必须直接说明。

这种写法不是为了让页面拥有更多格式，而是减少读者在执行过程中自行推断的内容。

## 审校先查事实，再看表达

审校既有文档时，Skill 使用固定的检查顺序：

1. **技术保真度**：检查命令、代码、链接、版本、前置条件、结果、术语和内部一致性；
2. **任务完整性**：确认目标、条件、操作、预期结果和必要的恢复路径齐全；
3. **信息架构**：检查标题层级、内容顺序、导航和重复信息；
4. **语言表达**：检查语态、时态、句子结构、术语一致性和包容性；
5. **内容呈现**：检查列表、表格、代码格式、界面标签、链接和图片说明；
6. **可访问性**：确认关键信息不只依赖颜色、位置、标点或图片表达。

这套顺序将“内容是否正确”与“表达是否专业”明确分开。Agent 不会因为一句话需要润色，就忽略其中未经验证的版本结论；也不会因为页面格式整齐，就认定读者已经拥有完成任务所需的全部信息。

如果用户只要求审校，Skill 只报告带位置和修改建议的问题，不会自动编辑文件。只有用户同时授权修改时，Agent 才会写回文档。这让只读评审与实际改动拥有清晰边界。

## 代码示例也属于技术事实

技术文档中的代码不是装饰。Skill 要求示例只包含完成当前任务所需的内容，并在文档承诺可运行时保证它确实可运行。

示例不能包含真实密钥、个人数据或生产端点，也不能使用没有解释的省略号假装代码完整。命令块不应混入 shell 提示符，示例输出需要明确说明是参考输出还是精确结果。对于占位符，Skill 推荐使用具有含义的大写名称，例如 `PROJECT_ID`，并在示例附近解释每个占位符。

界面操作同样需要精确。文档应使用界面上实际可见的标签，并通过“选择”“输入”“按下”等动作说明交互，而不是依赖控件的颜色、形状或屏幕位置。链接文字也应该脱离上下文后仍能说明目标，避免使用“点击这里”这类无法独立理解的文本。

这些要求共同指向一个原则：文档中的代码、界面和链接都是读者操作路径的一部分，必须像正文中的技术结论一样接受验证。

## 安装与调用

可以通过 `skills` CLI 从 Skill 仓库安装：

```bash
pnpm dlx skills add Hu-Wentao/skills \
  --skill write-technical-docs \
  --yes
```

当 `write-technical-docs` 已经安装并可被 Codex 发现时，可以在请求中直接指定它。起草一篇操作指南时，可以使用下面的提示：

```text
请使用 write-technical-docs Skill，为这个项目编写本地开发指南。
先检查现有 README、包管理器配置和项目命令，只记录能够验证的步骤。
读者是第一次接触该仓库的开发者；文档需要包含前置条件、启动步骤、
预期结果和常见失败的恢复方法。
```

审校现有文档时，可以收窄任务边界：

```text
请使用 write-technical-docs Skill 只读审校 docs/deploy.md。
先检查技术事实和任务完整性，再检查结构、语言和格式。
按严重程度列出问题、位置与建议修改，不要直接编辑文件。
```

如果要直接重写，则需要提供明确授权，并说明哪些项目事实不能改变：

```text
请使用 write-technical-docs Skill 重写 docs/api-quickstart.md。
保留现有 API 名称、请求字段和兼容性声明；重新组织信息顺序，
让读者可以从前置条件开始完成第一个请求，并在末尾验证响应。
```

提示中最有价值的信息不是“写得专业一些”，而是读者、目标、证据来源、编辑边界和预期产物。Skill 可以规范写作过程，但不能替使用者发明产品事实。

## 它适合哪些文档

`write-technical-docs` 适合创建、重写或审校以下内容：

- 教程、操作指南和概念说明；
- API、命令行和界面操作文档；
- README、故障排查说明和发布说明；
- 包含代码示例、命令、链接或截图的开发者内容；
- 需要统一信息结构、术语和可访问性的中文或英文技术文档。

它不是产品事实的来源，也不是代码测试、API 探测或版本兼容性验证的替代品。没有证据时，Skill 应该暴露不确定性；需要验证时，Agent 仍然要检查源码、运行允许执行的命令，或查询权威文档。

对于只需要宣传语、文学表达或品牌创意的内容，这套以任务完成和技术保真为中心的流程也未必合适。Skill 的目标是开发者文档，而不是覆盖所有写作类型。

## 交付前的最后检查

完成草稿后，Skill 还要求进行一次编辑检查。Agent 会确认开头是否说明结果，前置条件是否早于操作，标题和链接脱离上下文后是否仍有意义，命令、输出、界面标签和代码标识是否被正确区分。

它还会检查术语是否一致、缩写是否在需要时定义、日期和单位是否明确、图片是否包含有用的替代文本，以及正文是否出现未经证实的最佳、最快或未来功能承诺。

最终交付不仅要说明改了什么，还要说明技术事实依据什么得到验证，并列出尚未解决的假设。对于技术文档，这些信息比“已经完成润色”更能帮助下一位审阅者判断文档是否可以发布。

## 结语

高质量技术文档不是把正确的信息换一种好看的说法，而是建立从事实、读者任务到操作结果的完整路径。`write-technical-docs` 将这条路径拆成可执行的规则：项目约定优先，技术正确性先于编辑质量，规范按需加载，常见路径先于边界情况，操作与验证紧邻呈现，不确定事实不得被语言掩盖。

这套方法的价值不只在于让 Agent 写出更顺畅的句子。它让文档工作拥有可以重复的检查顺序，也让作者和审阅者能够区分：哪里是产品事实，哪里是编辑选择，哪里仍然缺少证据。

当这些边界清楚之后，技术文档才不只是对系统的描述，而会成为读者能够实际使用、验证和维护的工程接口。
